# Wisp

Тот же клиент, что и [Netegram](https://github.com/weholy/netegram) — тот же интерфейс, тот же код экранов, — но без MTProto и без серверов Telegram. Свой сервер, свой протокол, свой вход.

## Что уже сделано

- **`server/`** — рабочий бэкенд (Node.js + TypeScript): регистрация/вход, чаты один-на-один, сообщения в реальном времени по WebSocket, история сообщений. Проверено вручную end-to-end: вход → создание чата → отправка сообщения → доставка второй стороне в реальном времени → сохранение в базе.
- **`client/`** — исходник Netegram как есть, один в один. Пока всё ещё говорит по MTProto с серверами Telegram — замена сети описана ниже, это следующий и самый большой этап.

## Вход: номер Wisp через Telegram-бота

Без телефона и без SMS-провайдера. У аккаунта Wisp есть **номер Wisp** — строка вида `+79991234567`, но это не настоящий телефон: она никуда, кроме этого бота, не отправляется и ни с каким телеком не связана. Нужна как логин.

1. Пользователь открывает бота в Telegram (`@BotFather` → `/newbot`, вы заводите бота сами), жмёт `/start`.
2. Бесплатно — бот выдаёт случайный номер (США/Россия/другой вид на выбор случайно).
3. За 100 звёзд Telegram — открывается выбор: конкретная страна, «анонимный» вид, или свой номер целиком.
4. При входе в приложении пользователь вводит свой номер Wisp → сервер шлёт код через бота в тот же чат → пользователь вводит код в приложении.

Это обычный, документированный Telegram Bot API (`api.telegram.org/bot<token>/...`, включая нативную оплату Stars — `currency: "XTR"`), не MTProto. Аккаунты, чаты и сообщения полностью свои, на своём сервере; единственное, что связывает Wisp с Telegram, — этот один бот как канал доставки кода.

**Админ.** Chat id, перечисленные в `ADMIN_CHAT_IDS` (через запятую), получают доступ к платному выбору без оплаты и могут забрать себе любой номер, даже уже занятый другим аккаунтом, — тот при этом получает новый случайный автоматически, с уведомлением. Ставится только через переменную окружения при старте сервера, никакой кнопкой или командой в самом боте эту роль получить нельзя.

## Как запустить сервер

```sh
cd server
npm install
cp .env.example .env
npm run dev
```

Без `TELEGRAM_BOT_TOKEN` в `.env` сервер поднимется и будет работать (чаты, WebSocket), но бот не сможет ни выдать номер, ни прислать код — при попытке `/auth/request-code` вернёт `502 delivery_failed` вместо того, чтобы соврать об успехе.

**Получить токен:** в Telegram написать [@BotFather](https://t.me/BotFather) → `/newbot` → вставить токен в `.env`. Свой `chat_id` — написать боту `/start` один раз и посмотреть в базе (`SELECT telegram_chat_id FROM users`), затем вписать в `ADMIN_CHAT_IDS`.

База — SQLite-файл (`server/data/netegram.db` по умолчанию), создаётся сама при первом запуске. Для прод-нагрузки план — перейти на Postgres; слой доступа к данным уже собран так, чтобы это было заменой одного файла (`src/db/db.ts`), а не переписыванием запросов по всему проекту.

**Проверить логику бота без реального Telegram:** `npm test` — прогоняет всю машину состояний (бесплатный номер, оплата первым делом, повтор оплаты, коллизия номеров, права админа) синтетическими апдейтами, ничего реально не отправляя.

### API v1

| Метод | Путь | Что делает |
|---|---|---|
| POST | `/auth/request-code` | `{wispNumber}` → шлёт код через бота |
| POST | `/auth/verify` | `{wispNumber, code}` → `{token, user}` |
| GET | `/chats` | список чатов с превью последнего сообщения |
| POST | `/chats/direct` | `{wispNumber}` → id чата один-на-один (создаёт, если его ещё нет) |
| GET | `/chats/:id/messages` | последние 50 сообщений |
| WS | `/ws?token=...` | `{type:"send", chatId, text}` → рассылается всем участникам чата как `{type:"message", ...}` |

## Деплой на свой сервер

`server/Dockerfile` уже готов (сборка в два этапа, рантайм без dev-зависимостей). На своём VDS: скопировать `server/`, `docker build`, передать переменные из `.env.example` (`TELEGRAM_BOT_TOKEN`, `ADMIN_CHAT_IDS`, при желании `PORT`), примонтировать volume под `/app/data` для базы. Долгополлинг бота работает без домена и TLS-сертификата — веб-хук понадобится только если решите переключиться на него отдельно.

## План замены сети в клиенте

Это самая большая оставшаяся часть. Делать по одному вертикальному срезу за раз, с проверкой на каждом шаге, — а не одним большим патчем: клиент компилируется только в облачной сборке (~50 минут за попытку), и вслепую резать 1642 сгенерированные функции TL-протокола и 755 файлов, завязанных на схему Postbox, — верный способ потратить много часов на один незамеченный тайпо.

Порядок:

1. **Авторизация.** Заменить экран ввода номера/SMS-кода (`AuthorizationUI`) так, чтобы он звал новый `/auth/request-code` и `/auth/verify` вместо `auth.sendCode`/`auth.signIn` в MTProto. Самый маленький и самый безопасный первый шаг — почти не трогает остальной клиент.
2. **Транспорт.** `MtProtoKit`'s `Network`/`Connection` — на клиент нового WebSocket-протокола. Здесь `TelegramApi`'s 1642 TL-функций перестают быть нужны почти целиком; останется реализовать реальный список используемых операций (отправить сообщение, получить историю, список чатов) под новый протокол.
3. **Синхронизация.** `Postbox`'s `AccountStateManager` — сейчас обрабатывает `pts`/`qts`-последовательности Telegram; заменить на приём `{type:"message"}` по WebSocket и запись напрямую в локальную базу клиента.
4. **Дальше по важности:** медиа (фото/файлы), группы, звонки — каждое отдельным срезом поверх готовых первых трёх.

Функции этого форка, завязанные конкретно на протокол Telegram (анти-удаление через перехват `messages.setTyping`, фейк-активность через `acquireLocalInputActivity` и так далее — см. [netegram](https://github.com/weholy/netegram)), в этой ветке теряют смысл или требуют отдельного переосмысления под собственный протокол; в объём этого этапа не входят.
